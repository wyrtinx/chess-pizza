# Правила бекенду

Бекенд сайту Chess Pizza: API для вітрини, кошика, оформлення, профілю з бонусами та адмін-панелі. Пишемо його разом із Claude (вайбкодинг), тому правила — для обох: що вирішено, як писати код і коли зупинятися й питати.

Поведінка продукту — у `.claude/docs/SPEC.md`, дизайн — у Figma (див. `.claude/docs/design/HANDOFF.md`). **Якщо SPEC чогось не каже — питати, а не вигадувати** (наприклад, правила нарахування бонусів чи округлення).

## 1. Стек

| Що | Вибір |
| --- | --- |
| Рантайм, пакети, тести | **Bun** (не Node, не npm / pnpm / yarn). Лок-файл `bun.lock` — у git |
| Фреймворк | **NestJS 12**, TypeScript **6.x** `strict` (7 не підтримують Nest CLI і Swagger-плагін) |
| База | **PostgreSQL 18** |
| ORM | **Prisma** — остання стабільна версія (не `rc` / `dev`) |
| Валідація | `class-validator` + `class-transformer` |
| Документація API | `@nestjs/swagger` (CLI-плагін) + **Scalar** на `/docs` |
| Логи | `nestjs-pino` |
| Захист | `helmet`, `@nestjs/throttler`, CORS з білим списком |
| Пошта | **Resend** на проді, **Mailpit** локально й у тестах |
| Фонові задачі | `@nestjs/schedule` (чистка гостьових кошиків тощо) |
| Локальне оточення | Docker Compose: Postgres + Mailpit |

**Версії — найновіші стабільні** для кожного пакета (без `rc` / `beta` / `next` / `dev`). Перед установкою — `npm view <пакет> dist-tags`: `latest` буває rc, тоді ставимо з явною версією. Якщо залежність не допускає останню — беремо найновішу з допустимих, а виняток і причину записуємо в таблицю версій `.claude/docs/tooling/backend.md`.

Версії свіжі (Nest 12, Prisma 7+), тому перед використанням незнайомого API — **звірятися з актуальною документацією через context7**, а не з пам’яті.

### Особливості Bun
- **Збирання — `nest build`** (tsc + Swagger CLI-плагін), запуск зібраного — `bun dist/main.js`. Розробка — `nest start --watch --exec bun`. Запускати `.ts` напряму через Bun не можна: тоді CLI-плагін Swagger не спрацює і схеми в документації будуть порожні.
- Що Bun уміє сам — беремо з Bun, без нативних модулів: паролі — `Bun.password` (argon2id).
- Тести — `bun test`.

## 2. Структура бекенду

- Фронтенд отримує типи **тільки з `backend/openapi.json`** (через `openapi-typescript`), **ніколи з Prisma**. `@prisma/client` і згенерований клієнт не імпортуються за межами `backend/`.
- Окремий пакет `packages/shared` не заводимо, поки не з’явиться справді спільний код.

### Структура `backend/`

```
backend/
├─ src/
│  ├─ main.ts
│  ├─ app.module.ts
│  ├─ config/            схема й валідація env
│  ├─ common/            фільтри, guards, декоратори, пайпи, коди помилок
│  ├─ prisma/            PrismaModule / PrismaService
│  └─ modules/
│     ├─ auth/  users/  products/  cart/  orders/
│     ├─ bonuses/  pizzerias/  mail/  health/
├─ prisma/               schema.prisma, migrations/, seed.ts
├─ test/                 smoke-сценарії
├─ openapi.json          згенерований контракт API (у git)
├─ Dockerfile
└─ README.md
```

- **Модуль = предметна область.** Усередині: `*.module.ts`, `*.controller.ts`, `*.service.ts`, `dto/`. Окремого модуля «admin» немає: адмінські ендпоінти живуть у своїх доменних модулях під `/admin/...` і закриті `RolesGuard`.
- **Контролер тонкий:** прийняв DTO → викликав сервіс → повернув response DTO. Бізнес-логіка — тільки в сервісах.
- **Модуль не лізе в таблиці іншого модуля** — тільки через його експортований сервіс.
- **Чисті розрахунки** (ціна, підсумок, бонуси, переходи статусів) — окремими функціями без залежностей від Nest і Prisma: їх легко тестувати.

## 3. Конвенції API

- REST, префікс **`/api/v1`**. Шляхи — іменники в множині, kebab-case: `/api/v1/products`, `/api/v1/admin/orders/:id/status`.
- JSON у **camelCase**. Дати — ISO 8601 в UTC.
- **Гроші — цілі числа в копійках** у кожному полі й у кожній таблиці. Ніяких `float`. В описі поля в OpenAPI пишемо «у копійках».
- id — UUID. Для людей у замовлення є окремий короткий номер (`#1042`).
- Відповіді — тільки response DTO, **ніколи сирі моделі Prisma** (щоб не витекли `passwordHash` чи службові поля).
- Коди: `200` читання / зміна · `201` створення · `204` без тіла · `400` валідація · `401` не авторизований · `403` немає прав · `404` · `409` конфлікт (зайнятий e-mail, зміна статусу не по порядку) · `429` ліміт запитів.
- Списки, що ростуть (замовлення, історія, адмінка), — з пагінацією `limit` + `cursor`.
- `POST /orders` приймає заголовок `Idempotency-Key`: подвійний клік чи повтор запиту не створює двох замовлень.

### Формат помилок
Один для всього API:

```json
{
  "statusCode": 400,
  "code": "VALIDATION_FAILED",
  "message": "Validation failed",
  "details": [{ "field": "phone", "code": "PHONE_INVALID" }],
  "requestId": "…"
}
```

- `code` і `details[].code` — **машинні коди** з одного enum `ErrorCode`. Текст українською чи англійською підставляє фронтенд (тексти — у SPEC 3.6–3.10).
- `message` — коротко англійською, для розробника.
- Стек викликів клієнту не віддаємо ніколи.

## 4. Валідація

- Глобальний `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })`.
- Усе вхідне (body, query, params) описується DTO. Повідомлення кожного валідатора — код з `ErrorCode`, фільтр збирає їх у `details`.
- Правила збігаються зі SPEC: ім’я ≥ 2, пароль ≥ 8, e-mail `x@y.z`, адреса ≥ 5 і з номером будинку, ціна > 0.
- **Телефон:** приймаємо `+380XXXXXXXXX` або `0XXXXXXXXX` із пробілами, дефісами, дужками; зберігаємо й віддаємо в E.164 (`+380XXXXXXXXX`). Форматування для показу (E.123) — справа фронтенду.
- E-mail нормалізуємо: обрізаємо пробіли, нижній регістр.

## 5. Доменні правила

Числа беруться зі SPEC і живуть **в одному місці** — `pricing.constants.ts` (жодних магічних чисел у сервісах).

### Ціни й замовлення
- **Ціну рахує тільки сервер.** Ціни, що прийшли від клієнта, ігноруємо.
- Піца: розмір 25 / 30 / 35 см (−60 / 0 / +100 ₴ до бази 30 см), тісто, добавки (мультивибір).
- Самовивіз: −5 % від суми страв, доставка 0. Доставка: 79 ₴, безкоштовно від 600 ₴.
- Бонуси: тільки в користувача; «Списати» = `min(баланс, сума страв)`, доставку бонусами не оплачують.
- Округлення — в одній функції модуля розрахунків; правило уточнюємо в користувача, якщо SPEC не каже.
- Позиція замовлення зберігає **знімок**: назву, опції, ціну на момент покупки. Зміна чи видалення товару старих замовлень не чіпає.
- Створення замовлення — **одна транзакція**: замовлення + списання бонусів + очищення кошика.
- Статуси: `ACCEPTED → BAKING → ON_THE_WAY → DELIVERED`, плюс `CANCELLED`. Переходи — тільки вперед, таблиця переходів в одному місці; інший перехід → `409`.

### Кошик (на сервері)
- Гість отримує анонімний кошик: id у httpOnly cookie, сам кошик — у базі.
- Під час входу гостьовий кошик **вливається** в кошик користувача.
- Однакові позиції (товар + розмір + тісто + відсортовані добавки) склеюються за кількістю.
- Ціни перераховуються при кожній видачі кошика. Прихований чи видалений товар позначається як недоступний; при оформленні такі позиції не проходять із зрозумілою помилкою.
- Гостьові кошики, яких не чіпали 30 днів, видаляє крон.

### Товари
- «Сховати / Показати» — прапорець видимості; приховані не віддаються на вітрині.
- «Видалити» — soft delete (`deletedAt`) + прибрати товар з усіх кошиків.

### Ролі
- `USER` і `ADMIN`, перевірка через `RolesGuard`. Адміна створює seed (дані з env), e-mail адміна в коді не зашиваємо.
- Гість ніколи не бачить чужих даних: бонусів, адрес, історії.

## 6. Авторизація

- Паролі — `Bun.password` (argon2id).
- **Access JWT — 15 хв, refresh — 30 днів.** Refresh міняється при кожному оновленні (rotation), у базі лежить тільки його хеш; повторне використання старого refresh відкликає всю сесію.
- Обидва токени — у **httpOnly cookie**, `Secure` на проді, `SameSite=Lax`; refresh-cookie з `path` тільки на `/api/v1/auth`.
- Фронт і API деплоїмо **на одному домені** (`chesspizza.xxx` + `api.chesspizza.xxx`), щоб працював `SameSite=Lax`.
- **Код підтвердження пошти:** 6 цифр, у базі — хеш, живе 10 хв, 5 спроб, повторна відправка не частіше ніж раз на 60 с (сервер перевіряє сам і віддає `retryAfter`).
- Відновлення пароля — одноразовий код / токен із тими ж правилами (хеш, TTL, ліміт спроб); після зміни пароля всі сесії відкликаються.
- Вхід і відновлення **не розкривають**, чи існує акаунт («невірна пошта або пароль»). Реєстрація може повернути `EMAIL_TAKEN`.

## 7. Безпека

- `helmet`, CORS — тільки домени з env, `credentials: true`.
- `@nestjs/throttler` — жорсткі ліміти на вхід, реєстрацію, коди й відновлення пароля.
- Ліміт розміру тіла запиту.
- У логах **ніколи** немає паролів, токенів, кодів, cookie (redact у pino).
- Секрети — тільки в `.env` (не в git). У git — `.env.example` з усіма ключами без значень.
- Env перевіряється схемою при старті: без потрібної змінної застосунок не запускається.
- SQL — тільки через Prisma. `$queryRaw` — тільки tagged template, ніякої конкатенації рядків.

## 8. База даних

- Схема змінюється **тільки міграціями** (`prisma migrate dev`); застосовану міграцію не редагуємо — пишемо нову. На проді — `prisma migrate deploy`.
- Моделі — PascalCase в однині, поля — camelCase; таблиці й колонки в базі — snake_case через `@@map` / `@map`.
- У кожної таблиці `createdAt` / `updatedAt`, час — `timestamptz`, UTC.
- Seed: меню (товари з Figma / SPEC), піцерії для самовивозу, адмін.
- Налаштування Prisma (генератор, адаптер драйвера, шлях до клієнта) — за актуальною документацією поточної версії.

## 9. Помилки й логи

- Глобальний exception filter віддає формат із розділу 3. Помилки Prisma мапляться: `P2002` → `409`, `P2025` → `404`, решта → `500` без подробиць назовні.
- `nestjs-pino`: JSON-логи, `requestId` у кожному запиті (заголовок `X-Request-Id`, повертаємо його у відповіді).
- `GET /api/v1/health` — для хостингу й Docker healthcheck.

## 10. Пошта

- Уся пошта йде через один `MailService`. Транспорт обирає env `MAIL_TRANSPORT`: `mailpit` (локально й у тестах) або `resend` (прод).
- Resend працює тільки з **підтвердженим власним доменом**: без нього листи доходять лише на пошту власника акаунта.
- Шаблони листів — українською й англійською (мова з профілю користувача, у гостя — з `Accept-Language`). У кожного листа є HTML і текстова версія.
- Ключ Resend — тільки в env.

## 11. Документація API

- Контракт генерується з коду: `@nestjs/swagger` + CLI-плагін з `introspectComments`. **Руками в README ендпоінти не описуємо.**
- Кожен контролер — `@ApiTags`; кожен ендпоінт — короткий summary, response DTO і **всі можливі помилки** (з кодами `ErrorCode`). Авторизація через cookie описана як security scheme.
- JSDoc у DTO й контролерах — **українською** (він потрапляє в документацію). Решта коментарів у коді — англійською.
- Інтерфейс — Scalar на `/docs`, вмикається env `DOCS_ENABLED`.
- `bun run openapi` записує `backend/openapi.json`; після кожної зміни API файл оновлюється в тому ж коміті.
- `backend/README.md` — тільки запуск, змінні оточення, скрипти й посилання на `/docs`.

## 12. Тести

Бекенд не здається як робота, тому тести — **мінімальні, там, де вони реально ловлять помилки**:

- **Unit** (`bun test`) — тільки чисті розрахунки: ціна позиції, підсумок замовлення, знижка самовивозу, безкоштовна доставка, бонуси, склеювання позицій кошика, переходи статусів.
- **Smoke-сценарії** проти справжньої тестової бази (окрема БД у тому ж Postgres із Docker Compose): реєстрація → код → вхід; кошик → замовлення.
- Без вимог до покриття й без e2e на кожен ендпоінт. Решту Claude перевіряє руками: запити до ендпоінтів після кожної фічі + короткий звіт.
- **Перед «готово» обов’язково зелені:** `bun run typecheck`, `bun run lint`, `bun test`.

## 13. Стиль коду

- TypeScript `strict` + `noUncheckedIndexedAccess`. **Ніякого `any`** — `unknown` і звуження типу.
- ESLint (typescript-eslint) + Prettier; без «плаваючих» промісів.
- Імена файлів — kebab-case із суфіксами Nest (`orders.service.ts`, `create-order.dto.ts`). Один клас на файл, без `default export`.
- Усі залежності — через DI, без статичних синглтонів.
- Код, імена й коментарі — англійською (крім JSDoc для документації, див. розділ 11).

## 14. Деплой

- Один `Dockerfile` (multi-stage на образі `oven/bun`): збирання `nest build`, запуск `bun dist/main.js`.
- Уся конфігурація — через env; той самий образ працює локально й на проді.
- Перед стартом нової версії — `prisma migrate deploy`.
- Хостинг ще не обрано (кандидати: VM з `docker compose` або Render + Neon); код не залежить від конкретного хостингу.

## 15. Git

### Гілки
- **`main`** — стабільна. Вливає в неї **тільки користувач**, з `dev`, звичайним merge commit (не squash — інакше `dev` і `main` розійдуться).
- **`dev`** — робоча гілка.
- **Кожна задача бекенду — окрема гілка від свіжого `dev`:** `feat/<scope>-<коротко>`, `fix/…`, `chore/…` (типи — як у Conventional Commits).

### Хід задачі
1. Після «го» на задачу Claude оновлює локальний `dev` (`git pull`), створює гілку задачі, комітить і пушить її.
2. Claude дає **заголовок PR** у форматі Conventional Commits (після squash він стає повідомленням коміту в `dev`) і **опис**: що зроблено, як перевірено.
3. Користувач відкриває PR у `dev`, перевіряє й сам натискає **Squash and merge**.
4. Перед наступною задачею Claude видаляє локальну гілку влитої задачі (`git branch -D`: після squash git не бачить її як влиту).

**Claude ніколи не вливає в `dev` і `main`.**

### Загальне
- Поза цим процесом **Claude не запускає git-команди, що щось змінюють** (`init`, `add`, `commit`, `push`, `merge`, `reset` тощо), поки користувач прямо не скаже; тільки підказує команди. Читати (`status`, `diff`, `log`) можна.
- Коміти — Conventional Commits (`feat(orders): …`, `fix(cart): …`).
- `.env` і секрети в git не потрапляють ніколи.

## 16. Як працюємо з Claude

1. **Спочатку план, потім код.** Короткий план (які файли й що в них) → чекати «го» → робити все з плану. Що виходить за план — зупинитися й спитати.
2. **Одна фіча = закінчена вертикаль:** схема й міграція → сервіс → DTO → контролер → документація → тести на розрахунки (якщо є) → ручна перевірка ендпоінтів.
3. Після фічі — короткий звіт: що зроблено, як перевірено, що лишилося.
4. Неясність у SPEC чи дизайні — питання користувачу, а не здогадка.
